Reference

Server

brrrrr serve is one process that holds today's rows in memory and the rest in Parquet by day, and answers one query over both. It is what kdb+ splits into a tickerplant, a real-time database, a historical database and a gateway.

$ brrrrr serve --data ./data
brrrrr 0.1.0 serving ./data: http://127.0.0.1:4242 (the console, the API), postgresql://127.0.0.1:5433

Live tables

Write rows to a table by its name; the first write makes it, its columns and types from the rows. Rows are JSON lines or CSV.

$ curl -X POST localhost:4242/write/trades --data-binary @trades.jsonl
{"table":"trades","rows":2565}
$ curl -X POST 'localhost:4242/write/trades?format=csv' --data-binary @more.csv

A table's time is its first timestamp column, or the column ?time= names on the first write. Rows written are queried at once. Every write goes to a write-ahead log first, and every --flush interval (a minute by default) rows are moved to Parquet, one file set per day: data/trades/date=2024-01-02/…. A query over trades reads the day files and the rows in memory as one table. A stop flushes; a crash replays the log.

A write that does not fit the table (a missing column, text where a number goes) is refused whole, with the reason.

Live views

A live view is a query kept up to date. It runs over the rows so far, then on each row as it arrives, and emits each bar as it closes. Its answer is exactly the same query's over the table: the engine is the same.

CREATE LIVE VIEW bars AS
SELECT time_bucket('1m', ts) AS minute, symbol,
       first(price, ts) AS open, max(price) AS high, min(price) AS low,
       last(price, ts) AS close, sum(size) AS volume
FROM trades
GROUP BY minute, symbol;

A live view with time_bucket_gapfill fills a group's empty buckets when its next bucket closes. An as-of join at a time offset (t.ts + INTERVAL '5 seconds' >= q.ts) is refused: a live view matches each row as it arrives, before the quote it wants. Run markouts as queries, and window joins (JOIN LATERAL) too. A live view with lead emits a row once its partition's next row arrives.

What a live view emits is a live table of its own: query it, subscribe to it, or build views on it. Live views survive a restart, picking up where they stopped without repeating a row. DROP VIEW bars removes one.

Subscriptions

Two kinds, as server-sent events: any HTTP client, curl -N, or EventSource in a browser.

$ curl -N localhost:4242/subscribe/bars                      # each new row of a table or live view
data: {"minute":"2024-01-02T09:31:00Z","symbol":"BTC","open":42011.5,…}

$ curl -N 'localhost:4242/watch?q=SELECT%20count(*)%20FROM%20trades&every=1s'   # a query's answer when it changes
data: {"columns":["count(*)"],"types":["uint"],"rows":[[2565]],"elapsed_ms":0.4}
const bars = new EventSource("http://localhost:4242/subscribe/bars");
bars.onmessage = (e) => chart.update(JSON.parse(e.data));

PostgreSQL protocol

Clients that speak PostgreSQL connect, with the token (if the server has one) as the password, any user and database name, and TLS off. brrrrr answers in its own SQL, not PostgreSQL's; what a driver sends to set itself up (SET, BEGIN, SHOW server_version, SELECT version(), current_schema()) is answered as PostgreSQL 16 would.

$ psql "postgresql://localhost:5433/brrrrr" -c "SELECT * FROM bars ORDER BY minute DESC LIMIT 5"
import datetime, psycopg
with psycopg.connect("postgresql://localhost:5433/brrrrr") as con:
    since = datetime.datetime(2024, 1, 2, 9, 30, tzinfo=datetime.timezone.utc)
    rows = con.execute("SELECT symbol, last(price, ts) AS last FROM trades WHERE ts > %s GROUP BY symbol", [since]).fetchall()

Times come back as timestamptz, integers as int8, other numbers as float8, NULL as NULL, and an error with brrrrr's message. A query's parameters ($1, %s, ?) may be text, integers, floats, booleans, dates and timestamps, sent as text or binary; a time may carry a zone (2024-01-02T09:30:00Z, +01:00). Grafana

Add a PostgreSQL data source, in the UI or provisioned from a file in provisioning/datasources/:

apiVersion: 1
datasources:
  - name: brrrrr
    uid: brrrrr
    type: grafana-postgresql-datasource
    url: localhost:5433
    user: brrrrr
    jsonData: { database: brrrrr, sslmode: disable, postgresVersion: 1600 }
    secureJsonData: { password: change-me }   # the server's token, if it has one

A time-series panel of a live view, one series per symbol, and one of the trades in five-minute buckets. $__timeFilter, $__timeFrom(), $__timeTo() and $__timeGroupAlias work; $__unixEpochFilter is for columns of epoch numbers, which a time column is not:

SELECT minute AS time, symbol, close
FROM bars
WHERE $__timeFilter(minute)
ORDER BY minute
SELECT $__timeGroupAlias(ts, '5m'), symbol AS metric, avg(price) AS price
FROM trades
WHERE $__timeFilter(ts)
GROUP BY 1, 2
ORDER BY 1

Kafka

Ingest topics into live tables, one JSON object per message (Redpanda and other Kafka-compatible brokers work the same):

$ brrrrr serve --kafka localhost:9092 --ingest trades=md.trades --ingest quotes=md.quotes

For pipelines that produce to Kafka exactly once, see streaming pipelines.

History kept elsewhere

Name archive locations as tables beside the live ones: a query over both joins today's rows with years of history in S3.

$ brrrrr serve --data ./data -t history=s3://archive/trades/

A shared server

One heavy query must not hold up everyone else, nor the rows being written:

  • A time limit. A statement that runs longer than --query-timeout (5 minutes by default) stops, saying so. A PostgreSQL session lowers it for itself with SET statement_timeout = '30s' (a number is milliseconds).
  • Cancellation. A query stops when its client gives up: an HTTP client that closes its connection (the console's Stop, an interrupted curl, a closed tab), or a PostgreSQL CancelRequest (Ctrl-C in psql, a driver's cancel). It stops as it reads its next rows; a last step over everything read (sorting, exact percentiles) finishes first.
  • Turns. At most --max-queries statements run at once; the others wait their turn, within their time limit. If 16 times as many already wait, a new one is refused at once with the server is busy. Writes, Kafka ingest and live views never wait for a turn.

/metrics counts the statements stopped by each cause (brrrrr_statements_timed_out_total, _canceled_total, _abandoned_total), those refused (brrrrr_statements_refused_busy_total), and those running and waiting now.

Security

By default the server listens on 127.0.0.1 only. Before listening on other addresses, set a token: clients give it as Authorization: Bearer <token> over HTTP and as the password over PostgreSQL. Without one, anyone who reaches the ports may read and write. Put TLS in front with a reverse proxy.

In Docker

$ docker run -d -p 4242:4242 -p 5433:5433 -v brrrrr-data:/var/lib/brrrrr -e BRRRRR_TOKEN=change-me \
    ghcr.io/aperiodic-io/monotile serve --data /var/lib/brrrrr/serve --http 0.0.0.0:4242 --pg 0.0.0.0:5433

The image runs as an unprivileged user (uid 65534), which owns /var/lib/brrrrr: keep the data there. With Kafka and Grafana: a live dashboard in one docker compose up.
