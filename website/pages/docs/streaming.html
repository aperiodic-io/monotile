Reference

Streaming pipelines

brrrrr run runs a SQL pipeline from Kafka topics to Kafka topics: it reads each message as a row, runs your views over the rows as they arrive, and writes each result to a topic exactly once. Sources and sinks can also be Parquet files, on disk or in an object store. It checkpoints as it goes, so a crash, kill -9 or redeploy neither loses a message nor writes one twice.

$ brrrrr run bars.sql --checkpoints ./checkpoints
checkpoints: ./checkpoints/bars/2d73620a6f82043b
claimed the pipeline with checkpoint 1

An example: trades to bars

Trades arrive on the topic trades, one JSON object per message. One-minute OHLCV bars go to bars.1m, one JSON object per bar, each written once its minute has closed. This is examples/pipelines, whose README runs it against Redpanda in Docker, step by step.

CREATE EXTERNAL STREAM trades (
  time datetime64(3),
  symbol string,
  price float64,
  quantity float64
) SETTINGS type = 'kafka', brokers = 'localhost:19092', topic = 'trades', data_format = 'JSONEachRow';

CREATE EXTERNAL STREAM bars_1m (
  minute datetime64(3), symbol string,
  open float64, high float64, low float64, close float64, volume float64, trade_count uint64
) SETTINGS type = 'kafka', brokers = 'localhost:19092', topic = 'bars.1m', data_format = 'JSONEachRow',
  one_message_per_row = true;

CREATE MATERIALIZED VIEW bars INTO bars_1m AS
SELECT time_bucket('1m', time) AS minute, symbol,
       first(price, time) AS open, max(price) AS high, min(price) AS low,
       last(price, time) AS close, sum(quantity) AS volume, count(*) AS trade_count
FROM trades
GROUP BY minute, symbol;
$ rpk topic produce trades < trades.jsonl
$ rpk topic consume bars.1m --format '%v'
{"minute":"2024-01-02 09:30:00.000","symbol":"BTC","open":42011.5,"high":42020,"low":42011.5,"close":42020,"volume":0.75,"trade_count":2}
…

The view is plain brrrrr SQL: the same query over a file of the same trades, as a backfill or a research notebook runs it, gives the same bars. The engine is the same.

$ brrrrr sql -t trades=trades.jsonl "SELECT time_bucket('1m', time) AS minute, symbol, first(price, time) AS open, … FROM trades GROUP BY minute, symbol"

brrrrr validate bars.sql checks that a pipeline parses and every view compiles, and lists its sources (<-) and sinks (->), without connecting to anything.

Exactly once

Every --interval (10 s), brrrrr writes a checkpoint: the state of every open window, how far it has read each source partition, and how far each sink partition was written, as one file. On a restart it restores the newest checkpoint, reads each sink partition from the checkpointed offset to its end, and replays the sources from their checkpointed offsets; each message the replay produces again that is already in its topic is not written a second time. A message is known by its redpanda-dedup-key header if the sink gives it one (below), otherwise by its payload: a bar names its window and symbol, so it is unique.

  • Stopping. SIGTERM or Ctrl-C takes a last checkpoint and releases the pipeline, so a restart has nothing to replay.
  • Two instances. A checkpoint is also a lease. An instance started while another still runs the same pipeline (a rolling deploy, a pod not yet dead) waits until that one stops or misses three checkpoints (--takeover), then takes over. Two never write at once.
  • A changed SQL file starts from scratch: its checkpoints are kept under a hash of the file. Without a checkpoint, brrrrr replays what the sources still hold and reads the sinks back as far (at least --lookback hours), so it still writes nothing twice.
  • The first start does not write the windows that began before a source's oldest record: part of their input may be missing. It judges by the Kafka records' timestamps, so a producer that stamps records with their events' times gives whole windows from the first one. Records stamped when they were produced (the default) of events from long ago would hold back every window: pass --partial-windows to write them all.

The SQL

A pipeline is a file of statements. They declare the topics and streams the way Timeplus Proton does (pipelines written for Proton run unchanged); a view's query is brrrrr's own SQL or Proton's.

StatementIs
CREATE EXTERNAL STREAM name (columns) SETTINGS type = 'kafka', …A Kafka topic: a source if it is read, a sink if a view writes into it.
CREATE EXTERNAL STREAM name (columns) SETTINGS type = 'file', data_format = 'Parquet', path = …Parquet files: a source if it is read, a sink if a view writes into it (below).
CREATE STREAM name (columns)A stream between views, held in memory.
CREATE MATERIALIZED VIEW name INTO target AS SELECT …A query over a stream, its rows written into target, a stream or a sink.

IF NOT EXISTS is accepted and changes nothing. Views receive rows in the order they are created.

Sources

The settings of a Kafka stream: type = 'kafka', topic, brokers (or --brokers), data_format, and seek_to = 'earliest' (the default: a first start reads the topic from its start) or 'latest'. A source's data_format is 'JSONEachRow': each message is one JSON object, read as ClickHouse reads one.

  • Fields are matched to the declared columns by name. A field not declared is ignored. A declared one that is missing or null is the column's default (0, '', 1970-01-01), or NULL in a nullable(…) column.
  • A datetime is text: 2024-01-02 09:30:00.123, or ISO 8601, 2024-01-02T09:30:00.123Z or with an offset such as +01:00; without either it is UTC. Or a number: an integer counts the column's own unit since 1970, milliseconds in a datetime64(3), microseconds in a datetime64(6), seconds in a datetime; a number with a fraction counts seconds (1704187800.123).
  • A number may also come as text ("42.5"), and a non-string value in a string column is its JSON text.
  • A message that is not a JSON object, or a value that fits no column ("n/a" as a price, an unreadable time), is skipped, logged (once a second at most) and counted in brrrrr_decode_errors_total.

Types: int8 to int64, uint8 to uint64, float32, float64, bool, string, datetime, datetime64(p) (up to microseconds, p ≤ 6), array(t), nullable(t), and low_cardinality(t), which is t. Protobuf sources (data_format = 'ProtobufSingle', format_schema = 'file:Message') take the .proto file with --proto.

Sinks

A sink is data_format = 'JSONEachRow' with one_message_per_row = true: one message per row, a JSON object of the sink's columns in their order, a datetime as text in its column's precision. A column _tp_message_headers map(string, string) sets the message's Kafka headers instead of being written; its header redpanda-dedup-key is then the message's identity for exactly once, rather than its whole payload:

CREATE EXTERNAL STREAM bars_1m (
  window_start datetime64(3), symbol string, close float64,
  _tp_message_headers map(string, string) MATERIALIZED
    cast((['redpanda-dedup-key'], [concat(to_string(window_start), '|', symbol)]), 'map(string, string)')
) SETTINGS type = 'kafka', topic = 'bars.1m', data_format = 'JSONEachRow', one_message_per_row = true;

A MATERIALIZED column is computed from the row on every write; a DEFAULT one when the view has no column of its name. A sink column the view does not name gets its type's default.

Parquet files

A file stream reads or writes Parquet files under its path: a directory, a glob, or a URL (s3://, gs://, az://, credentials from the environment as for brrrrr sql). It is a source if a view reads it, a sink if a view writes it. examples/pipelines/parquet.sql turns trades in files into bars in files, a directory a day:

CREATE EXTERNAL STREAM trades (time datetime64(3), symbol string, price float64, quantity float64)
SETTINGS type = 'file', data_format = 'Parquet', path = 'trades/';

CREATE EXTERNAL STREAM bars (day string, minute datetime64(3), symbol string, open float64, high float64,
  low float64, close float64, volume float64, trade_count uint64)
SETTINGS type = 'file', data_format = 'Parquet', path = 'bars/', partition_by = 'day';
SettingOfIs
pathbothWhere the files are. A sink's is a directory, not a pattern.
time_columna sourceWith several file sources, each one's time column (a datetime or an integer): their rows go in merged in time order, as an ASOF JOIN of trades to quotes needs.
partition_bya sinkColumns, comma-separated, whose values make a Hive directory each (day=2024-01-02/), as COPY … (PARTITION_BY …) writes them; the files then do not hold those columns, and brrrrr sql reads them back from the directory names.

A source reads its files in name order, a batch at a time, and then the files that land there later: name them so that they sort in time order (trades/2024-01-02T09.parquet, …), and put each in place whole (write it under another name, then rename it). A file that appears named before one already read is not read, and said. A file that does not read (a truncated one) is counted in brrrrr_decode_errors_total and read again a second later. A source's columns are read by name, cast to the declared types, and NULL where a file has none. A pipeline reads Kafka topics or files, not both; --max-drift and --iggy are for topics.

A sink writes the rows of each checkpoint interval (--interval) to new files, one per directory, named <pipeline>.<epoch>.<token>.parquet: row groups are encoded as the rows come, and the files are moved (or uploaded) into place before their checkpoint is written. Fewer, larger files take a longer --interval, or a compaction with brrrrr sql "COPY (FROM 'bars/') TO 'bars.parquet'".

Exactly once. A checkpoint is written only once the files of every row before its cut are in place. A crash after a checkpoint's files were put in place and before it was written leaves files whose rows the restart produces again: on restore, the pipeline deletes its own files of epochs after the checkpoint it restored, then replays. So each row is in the files once, whatever kills the pipeline; between a crash and its restart, a reader may see rows that are then deleted and written again. A start without a checkpoint (a first start, --fresh, a changed SQL file) deletes nothing: what its replay produces again is written again. Of a file source, the checkpoint holds the file being read and the rows read of it.

Views

A view's query is the SQL brrrrr sql takes (the reference), with the pipeline's streams as its tables: WHERE, GROUP BY time_bucket(width, time) and keys, every aggregate (first(x, time), last, vwap, percentiles, …), HAVING, ASOF JOIN of another stream, CASE, CTEs and subqueries:

CREATE MATERIALIZED VIEW markouts INTO markouts_5m AS
SELECT time_bucket('5m', t.time) AS minute, t.symbol,
       avg((t.price - (q.bid + q.ask) / 2) / ((q.bid + q.ask) / 2) * 1e4) AS slippage_bps,
       count(*) AS trades
FROM trades t ASOF JOIN quotes q ON t.symbol = q.symbol AND t.time >= q.time
WHERE t.quantity > 0
GROUP BY minute, t.symbol
HAVING count(*) >= 10;
  • Its result's columns go into the target's by name; a target column it does not name gets its type's default.
  • A window is written once, when a row of a later window arrives (EMIT AFTER WINDOW CLOSE WITH DELAY INTERVAL '1' SECOND after the query waits that much longer). The pipeline's clock is the newest event time it has read, and rows should come in about time order: a row for a window already written is late, dropped and counted in brrrrr_late_events_total. A stream that goes quiet keeps its last window open until its next row; --idle-close closes it after that many seconds of silence.
  • A stream never ends, so what needs a whole table is refused, with what to write instead: GROUP BY without time_bucket (a total over every row), a JOIN on keys alone (a lookup of the whole right table), an ASOF JOIN at a time offset, ORDER BY and LIMIT, and files as tables.

Views in Proton's dialect

A view that groups over tumble(...), and one that does not group, is read as Proton reads it:

SELECT window_start, symbol, vwap(price, quantity) AS vwap
FROM tumble(trades, time, 5m)
GROUP BY window_start, symbol
EMIT AFTER WINDOW CLOSE WITH DELAY INTERVAL '500' MILLISECOND
  • tumble(stream, time, width): back-to-back windows of width (15s, 1m, 5m, 1h, 1d; quoted or not) over the datetime column time. Each window has window_start and window_end; group by window_start and your keys. EMIT AFTER WINDOW CLOSE is required.
  • Aggregates: count(), sum, avg, min, max, earliest and latest (the first and last value read), vwap(price, size), twap, arg_min, arg_max, median, quantile(p)(x), quantile_t_digest(p)(x), quantile_exact(p)(x), uniq_exact, stddev, variance, corr, and the _if forms of those of one argument, such as sum_if(quantity, side = 'buy').
  • A windowed view takes no WHERE or HAVING: filter in a view into a CREATE STREAM and window that.

brrrrr validate says what a pipeline does not take, for every view, before it runs.

/metrics counts messages received (brrrrr_received_events_total), sent, late, failing to decode, checkpoints and their size, and the consumer lag. /health answers ok until the pipeline's loop has stalled for two minutes.

On Kubernetes

Run each pipeline as a StatefulSet of one, its SQL from a ConfigMap and its checkpoints on a PersistentVolumeClaim at /var/lib/brrrrr. The image runs as uid 65534: set fsGroup: 65534 so it can write there. Point the liveness probe at /health on port 9464, and give the pod time to take its last checkpoint on SIGTERM. A rolling deploy is safe: the new pod waits for the old one to release the pipeline. A lost volume is not an outage either: the pipeline starts without a checkpoint and writes nothing twice.

spec:
  template:
    spec:
      securityContext: { fsGroup: 65534 }
      terminationGracePeriodSeconds: 60
      containers:
        - name: brrrrr
          image: ghcr.io/aperiodic-io/monotile
          args: [run, /etc/brrrrr/pipeline.sql, --kafka-config, "@/etc/brrrrr-secrets/kafka.properties"]
          volumeMounts: [{ name: state, mountPath: /var/lib/brrrrr }, …]
          livenessProbe: { httpGet: { path: /health, port: 9464 } }
  volumeClaimTemplates:
    - metadata: { name: state }
      spec: { accessModes: [ReadWriteOnce], resources: { requests: { storage: 1Gi } } }

Checkpoints in an object store instead (--checkpoints s3://bucket/prefix, credentials from AWS_*) work with the published image (ghcr.io/aperiodic-io/monotile, built with object store support) and need no volume.

Pipelines or live views?

The live views of brrrrr serve run the same engine: the simpler choice when the results are for people and dashboards. One server ingests the rows (over HTTP, or from Kafka at least once), keeps the results as tables to query and subscribe to, and writes them to Parquet. brrrrr run is for results that other systems consume from Kafka: written exactly once, from Kafka to Kafka, one process per pipeline, scaled out and redeployed like any other consumer.
