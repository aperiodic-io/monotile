Reference

Files and object stores

brrrrr queries files where they are. There is no load step and no format of its own: what you query is what you keep, and what it writes any tool reads.

Formats

FormatReadWriteNotes
ParquetyesyesColumns are read in parallel, row groups decoded side by side. Written with zstd.
CSVyesyesHeader and types inferred; comma, tab, semicolon or pipe found by itself; .gz read as it streams.
JSON linesyesyesOne object per line (.json, .jsonl, .ndjson).
Databento DBNyesno.dbn, .dbn.zst (below).

The format comes from the name. For a file named otherwise, say it: read_parquet('…'), read_csv('…', delim = '|'), read_json('…'). DuckDB's read_csv_auto, read_ndjson and parquet_scan work too.

Reader options

DuckDB's options, after the path: read_csv('export.txt', header = false, skip = 1, delim = ';', nullstr = ['NA', 'null']).

OptionWhat it does
header, delim, quote, escape, skipThe file's layout (lines skipped before the header). Without a header the columns are column0, column1, ...
types = {'ts': 'TIMESTAMP'}Some columns' types; columns = {'a': 'BIGINT', ...} names and types them all.
timestampformat = '%d/%m/%Y %H:%M'How times are written (%Y %m %d %H %M %S, %f µs, %n ns).
nullstrThe texts that are NULL (by default an empty field).
union_by_name = trueFiles whose columns differ, read by name (below).

Text that is all times is read as times: ISO 8601, kdb+'s 2024.01.02D09:30:00.123456789, nanoseconds kept to the microsecond. Times written as numbers since the epoch, as many exchanges' downloads have them, are read with their unit, and stream in time order like any time column:

SELECT time_bucket('1m', timestamp) AS minute, last(price, timestamp) AS close, sum(amount) AS volume
FROM read_csv('trades_2024-01-01_BTCUSDT.csv.gz', types = {'timestamp': 'TIMESTAMP_US'})
GROUP BY minute;

A value that is not of its column's type is an error that names the file, the line and the column.

Files whose columns differ

Across a glob or a directory, the columns are the first file's: one a later file lacks is NULL in its rows, one it adds is left out, and one of another type is an error that says what to write. union_by_name = true reads every file's columns by name, a number of two kinds as a double and anything else as text, as DuckDB does: read_parquet('archive/*.parquet', union_by_name = true).

Locations

FROM 'trades.parquet';                         -- a file
FROM 'archive/2024-01-*.csv.gz';               -- a glob (* ? [..] and ** for any depth)
FROM 'trades/';                                -- a directory: every file under it
FROM 's3://bucket/trades/date=2024-01-02/';    -- S3, MinIO, Cloudflare R2
FROM 'gs://bucket/trades/*.parquet';           -- Google Cloud Storage
FROM 'az://container/trades/*.parquet';        -- Azure Blob Storage (also abfss://)
FROM 'https://example.com/trades.csv';         -- any URL

Hive partitions

A directory of key=value folders, as Spark, Hive and most archives lay out data, gives each folder's keys as columns:

trades/
  date=2024-01-02/symbol=BTC/part-0.parquet
  date=2024-01-02/symbol=ETH/part-0.parquet
  date=2024-01-03/…
SELECT date, symbol, count(*) FROM 's3://bucket/trades/' GROUP BY date, symbol;

A WHERE on a partition key reads only the folders it names.

Iceberg and Delta tables

An Apache Iceberg or Delta Lake table is read as its metadata says, from a directory or a store, with no catalog or service in between:

FROM delta_scan('s3://bucket/lake/trades');                -- Delta Lake: its _delta_log
FROM iceberg_scan('s3://bucket/warehouse/db/trades');      -- Iceberg: its newest metadata
FROM iceberg_scan('…/metadata/00002-….metadata.json');     -- Iceberg: that snapshot
FROM 's3://bucket/lake/trades';                            -- either, found by what is there

A Delta table is its log replayed from its latest checkpoint: the files added and not removed since, their partition values from the log. An Iceberg table is its current snapshot's data files, from its manifests; a table copied elsewhere is read where it is. A WHERE on the partitions (Delta's, Iceberg's identity partitions) reads only theirs, as for Hive directories. What changes rows beyond their files is refused with a message rather than misread: Delta's deletion vectors and column mapping, Iceberg's delete files (compact the table first).

Databento DBN

DBN files, as Databento delivers US equities and futures data, are read as they are, zstd-compressed or not, from a disk or a store: the trades, tbbo, mbp-1, mbp-10, mbo and ohlcv schemas. Their columns are those of Databento's own CSV and Parquet exports: ts_recv and ts_event as times (nanoseconds read to the microsecond), prices as numbers (185.64, not 185640000000), bid_px_00 and its kin for the book's levels, and symbol, each record's instrument as the file's symbology maps it (its instrument_id stays too).

-- one-minute bars from a day of trades
SELECT time_bucket('1m', ts_event) AS minute, symbol,
       first(price, ts_event) AS open, max(price) AS high, min(price) AS low,
       last(price, ts_event) AS close, sum(size) AS volume
FROM 'xnas-itch-20240102.trades.dbn.zst'
GROUP BY minute, symbol;

-- each trade with the quote it met
SELECT t.ts_event, t.symbol, t.price, q.bid_px_00 AS bid, q.ask_px_00 AS ask
FROM 'xnas-itch-20240102.trades.dbn.zst' t
ASOF JOIN 'xnas-itch-20240102.mbp-1.dbn.zst' q ON t.symbol = q.symbol AND t.ts_event >= q.ts_event;

Time order

Time-series data is usually written in time order, and brrrrr reads it that way: bars and windows stream through without sorting. Files out of order, or a time column that is not, are sorted once when a query needs it; nothing is misread.

Credentials

brrrrr reads each cloud's settings from the environment, as its own command-line tools do.

S3AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN, AWS_REGION; AWS_SKIP_SIGNATURE=true for public buckets
MinIO, R2, other S3-compatible storesas S3, plus AWS_ENDPOINT_URL (https://<account>.r2.cloudflarestorage.com, http://localhost:9000)
Google Cloud StorageGOOGLE_SERVICE_ACCOUNT (a key file's path) or GOOGLE_SERVICE_ACCOUNT_KEY (its JSON)
AzureAZURE_STORAGE_ACCOUNT_NAME with AZURE_STORAGE_ACCOUNT_KEY or AZURE_STORAGE_SAS_KEY

A refused credential says so, and names the variables to check. An endpoint that does not answer fails within seconds rather than hanging.

The cache

A Parquet file in a store is never downloaded whole: its footer is read, then only the column chunks of the columns and row groups a query reads, several requests at a time, straight from the store. Two columns of ten cost a fifth of the file, and a query of every column, fetched in parallel, comes sooner than one download of the whole: on a store answering in 25 ms at 100 MB/s a connection, two columns of a 200 MB file came in 0.9 s rather than 4.7 s, every column in 2.3 s rather than 5.4 s. CSV and JSON in a store are downloaded, and so are Parquet files under 16 MiB at an http(s):// URL, as a web server may not answer ranges (BRRRRR_RANGED_FROM sets that size, in bytes).

What is read is kept in a cache, the chunks of a Parquet file as a whole file is, so a query asked again fetches none. A changed object (a new ETag) is fetched again. The cache lives in ~/.cache/brrrrr (XDG_CACHE_HOME, %LOCALAPPDATA% on Windows), or where BRRRRR_CACHE says.

It keeps to 10 GiB: past that, the files used least recently are deleted, never one a query is reading, in this process or another sharing the cache. BRRRRR_CACHE_SIZE sets another size (50G, 500M); 0 keeps no cache: a Parquet file's chunks are read in memory only, any other remote file from a temporary copy deleted when the query is done. To empty it, delete the directory: rm -rf ~/.cache/brrrrr.

Writing

Write a result with COPY, or -o on the command line, to a file or straight to an object store. The format comes from the name, or FORMAT:

COPY (SELECT * FROM 'trades.csv.gz' WHERE symbol = 'BTC') TO 's3://bucket/btc.parquet';
COPY bars TO 'bars.csv';
COPY (FROM 'trades.csv') TO 'out/trades.data' (FORMAT parquet);
$ brrrrr sql -f bars.sql -o gs://bucket/bars/2024-01-02.parquet

Large results go up in parts, so memory stays flat whatever their size.

PARTITION_BY writes a directory of Hive partitions, as DuckDB does: a file per partition, its values in the path rather than in the file. This is how raw files become a date-partitioned archive (kdb+'s HDB), one day or many at a time; a WHERE on the partitions then reads only theirs:

COPY (SELECT strftime(ts, '%Y-%m-%d') AS date, * FROM 'raw/trades-*.csv.gz')
TO 's3://bucket/trades' (FORMAT parquet, PARTITION_BY (date, symbol));
-- s3://bucket/trades/date=2024-01-02/symbol=BTC/data_0.parquet, ...

COPY (SELECT strftime(ts, '%Y-%m-%d') AS date, * FROM 'raw/trades-2024-01-03.csv.gz')
TO 's3://bucket/trades' (FORMAT parquet, PARTITION_BY (date, symbol), OVERWRITE_OR_IGNORE);

SELECT symbol, vwap(price, size) FROM 's3://bucket/trades/' WHERE date = '2024-01-03' GROUP BY symbol;

A directory that holds files is written into only with OVERWRITE_OR_IGNORE, which replaces the partitions written again and keeps the others. Values are escaped as DuckDB escapes them (%20 for a space), NULL is __HIVE_DEFAULT_PARTITION__, and both read back as they were.

To a store, a result is uploaded as it is written, never through a local file: in one request up to 5 MiB, past that in parts of 5 MiB, one sent while the next is written (about 10 MiB of memory a file being written). The object is there once it is whole, never in part: a COPY that fails leaves nothing, its parts deleted. On disk, a file is written beside its place, hidden, and moved there once it is whole.

COPY writes as the query runs: rows are written a row group at a time, the columns of each compressed side by side, so a result of any size is written in a few hundred MiB (10M rows: 0.8 s and 350 MiB, DuckDB 1.4 s and 1.2 GiB). A query ordered by its outermost ORDER BY, or by time across its tables, is whole before it is written. With PARTITION_BY, 100 files are open at most: past them, the least recently written is closed, and its partition's later rows go to a file of the next number (data_1.parquet).

How it is tested

Every store is tested against an emulator in CI: MinIO-compatible S3 (versitygw), fake-gcs-server and Azurite, plus plain HTTP. The scenarios cover globs, Hive directories, each format written and read back, results uploaded in parts, Parquet read by ranges, changed objects, refused credentials and unreachable endpoints (object_stores.feature).
