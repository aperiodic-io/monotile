Introducing brrrrr

brrrrr is a SQL engine for tick data and other time series. It queries Parquet, CSV and JSON where they are, on disk or in object stores; it runs the same query live, as rows arrive; and it runs it as an exactly-once pipeline from Kafka to Kafka. Today we are opening it under Apache-2.0.

Why we built it

Market-data metrics (bars, VWAP, order flow, slippage, funding) are wanted live and over years of history. That usually means two systems: a streaming engine for the live numbers, and a batch engine such as DuckDB over Parquet for backfills and research. Two engines mean two dialects of SQL, and two answers to the same question that do not always agree: a bar computed live is not quite the bar the backfill wrote.

So we wrote one engine that does both. It started as a streaming engine, with exactly-once output and checkpoints. Then it learned to run ad-hoc SQL over files, by compiling each query into the views it already runs live, so a backfill gives what live gave. The problem is not ours alone, so we are opening it.

What did each trade pay against the mid? An ASOF JOIN pairs each trade with the last quote of its symbol at or before it:

$ brrrrr sql "SELECT t.symbol, count(*) AS trades,
                     avg(CASE WHEN t.side = 'buy' THEN 1 ELSE -1 END
                         * (t.price - (q.bid + q.ask) / 2)
                         / ((q.bid + q.ask) / 2)) * 1e4 AS cost_bps
              FROM 'trades.csv' t
              ASOF JOIN 'quotes.csv' q ON t.symbol = q.symbol AND t.ts >= q.ts
              GROUP BY t.symbol ORDER BY t.symbol"

From Python, a DataFrame in a variable is a table, and results come back as Polars, pandas or Arrow:

quotes = pl.read_csv("quotes.csv", try_parse_dates=True)

    SELECT symbol, avg((ask - bid) / ((ask + bid) / 2)) * 1e4 AS spread_bps
    FROM quotes GROUP BY symbol ORDER BY symbol

Live, the same query keeps its answer as rows arrive. brrrrr serve holds live tables; a live view runs over the rows so far, then on each new one, and emits each bar as it closes:

$ brrrrr serve --data ./data &
$ curl -X POST 'localhost:4242/write/trades?format=csv' --data-binary @trades.csv
{"table":"trades","rows":2565}
$ curl -X POST localhost:4242/query --data "CREATE LIVE VIEW bars AS
    SELECT time_bucket('1m', ts) AS minute, symbol, last(price, ts) AS close, sum(size) AS volume
    FROM trades GROUP BY minute, symbol"
$ curl -N localhost:4242/subscribe/bars        # then a trade at 00:30:05 closes the 00:29 bars
data: {"minute":"2024-01-01T00:29:00Z","symbol":"BTC","close":42397.2663,"volume":10.77}

The views are tables: query them over the PostgreSQL protocol from psql, Grafana or any driver, or watch them in the browser console at localhost:4242.

One SQL, three ways to run it

  • Ad hoc, over files and object stores: brrrrr sql, the shell, Python and Jupyter (%%sql).
  • Live, in a server: live tables written over HTTP or from Kafka, live views, subscriptions, the PostgreSQL protocol.
  • As a pipeline: brrrrr run reads Kafka topics, runs the views, and writes their rows to Kafka exactly once, with checkpoints that survive kill -9.

All three compile the query into the same views and run them in the same engine. A backfill over last year's files gives the bars the live view would have given.

Your files, in place

There is no import step and no storage format of ours. brrrrr reads Parquet, CSV (gzipped too) and JSON lines, single files, globs and Hive-partitioned directories, on disk, in S3 (and MinIO and R2), GCS, Azure, or at a URL; Delta and Iceberg tables too. COPY ... TO writes Parquet back, partitioned by date if you like. The data stays yours, in formats every other tool reads.

The kdb+ vocabulary, in SQL

Tick data has its own verbs: as-of joins, time buckets, first and last by time, VWAP, forward fill. kdb+ has them in q; most SQL engines have some of them, spelled differently. brrrrr has them in SQL: ASOF JOIN (strict, with a tolerance, or at an offset for markouts), time_bucket in any time zone, first(x, ts) and last(x, ts), vwap, twap, locf and gap filling, ema, window functions, exact percentiles. Coming from kdb+ maps one to the other; the cookbook has {{recipes}} recipes, each checked against DuckDB's answer.

The benchmarks, plainly

On a synthetic day of 10 million trades and 20 million quotes, brrrrr computes one-minute bars and hourly VWAP about 1.6 times faster than DuckDB, and per-symbol transaction costs (an as-of join) faster in half the memory. It is slower on plain group-bys, filters and arithmetic over every row, where DuckDB's vectorized aggregation is very good, and on a single total after an as-of join. The benchmarks page has every query, memory, the method and the scripts, with DuckDB, Polars and ClickHouse side by side.

What brrrrr is not

  • Not a general-purpose database. No transactions, updates or deletes; rows are appended. Its SQL is narrower than a database's: no full outer joins or many-to-many joins, no correlated subqueries. What it cannot run, it refuses with the reason and what to write instead.
  • Not a cluster. A query runs on one machine, on all its cores. Scale out by running a pipeline per feed, or a query per partition.
  • Not q. If you live in q, brrrrr will not replace it; if your team writes SQL and keeps data in Parquet, it may replace the parts of kdb+ you use.
  • Young. The streaming engine and its exactly-once pipelines are the most tested parts. The SQL shell, the Python package and the server are new; their interfaces may change before 1.0. The roadmap says what comes next.
