Where brrrrr is fast, and where it is not

brrrrr against the engines people use on one machine (DuckDB, Polars, ClickHouse's clickhouse-local), each query written as that engine's users write it. Where brrrrr is slower is below too.

Ad-hoc SQL over Parquet

A synthetic day of 10 million trades and 20 million quotes over 100 symbols (activity skewed as markets are), in Parquet with zstd. Each query runs as a user runs it, in a fresh process timed whole: brrrrr sql "…"; DuckDB's SQL from Python; Polars' own API over lazy scans (group_by_dynamic for bars, join_asof for as-of joins); ClickHouse's SQL in clickhouse-local (toStartOfMinute, argMax, ASOF JOIN). Median of three, 8 threads each; every engine's answer is checked to have the same rows as brrrrr's. Seconds, lower is better; the fastest in bold.

What the numbers say:

  • Time-bucketed aggregates are faster. Bars and VWAP stream through the table in time order and close each bucket as it ends: 1.6x DuckDB.
  • As-of joins per symbol are faster, in half the memory. The join runs per symbol, side by side.
  • Plain scans and group-bys are slower, and take more memory: DuckDB's vectorized hash aggregation is very good, and brrrrr reads rows into its streaming engine's form. This is the next thing we are working on.
  • A global aggregate after an as-of join is slower: it cannot run per symbol.

Method

  • Same machine, same files from the page cache, nothing else running.
  • Whole processes, as a user runs a query: start-up, planning and reading included.
  • Peak memory is the process's maximum resident set.
  • Answers compared, so neither side skips work.
